## 지금 바로 돌려 보기

API 키가 하나도 없어도 파이프라인 전체가 끝까지 돕니다. 목 모드는 **표준 라이브러리만** 씁니다.

```bash
# 1) 제도 페이지 생성 (목 데이터 중 중앙부처 25건)
python3 scripts/run_all.py

# 2) 사이트 빌드
bundle install
bundle exec jekyll serve --future
# → http://localhost:4000/walapp/
```

주요 환경변수:

| 변수 | 기본값 | 설명 |
|------|--------|------|
| `MOCK_DATA` | 자동 | `DATA_GO_KR_API_KEY` 가 없으면 자동으로 목 모드. `1`/`0` 으로 강제 가능 |
| `REGION_SCOPE` | `national` | 발행 범위. 중앙부처 우선 방침의 구현체. 지자체 포함은 `national,sido,sigungu` |
| `SYNC_SINCE` | (없음) | `YYYY-MM-DD`. 이 날짜 이후 수정된 제도만 받는 증분 동기화 |
| `BOJO24_BASE_URL` | 실 API | 엔드포인트 override (로컬 복제 서버 테스트용) |
| `BOJO24_PER_PAGE` | 1000 | 목록 한 페이지 요청 건수. 서버가 깎으면 자동으로 낮춘다 |
| `PUBLISH_MODE` | `theme` | `theme`: 테마 조별 발행 / `top`: 상위 N건 일괄 (초기 백필용) |
| `PER_THEME_LIMIT` | 1 | `theme` 방식에서 테마당 발행 건수 |
| `UPCOMING_LIMIT` | 1 | 시행 예정 발행 건수. 후보가 없으면 0건 |
| `PUBLISH_LIMIT` | 5 | `top` 방식 발행 상한 |
| `REFRESH_LIMIT` | 10 | 하루 갱신 상한 |
| `POST_DATE` | 오늘(KST) | 기준 날짜 override |
| `DRY_RUN` | 0 | `1` 이면 파일을 쓰지 않음 |

## 발행 정책

### 무엇을, 몇 건, 어떤 순서로

| 구분 | 하루 발행량 | 순서 기준 |
|------|------------|----------|
| 시행중 | 오늘 조의 테마 4개마다 1건씩 = **4건** | 원천 조회수 백분위 |
| 예정 | 상위 **1건** (후보 없으면 0건) | 원천 조회수 백분위 |
| 종료 | 상태만 갱신 (**전량**, LLM 미사용) | — |

테마 8개를 4개씩 두 조로 나눠 하루씩 번갈아 돕니다 (`taxonomy.AUDIENCE_GROUPS`).

```
짝수일: 청년 · 양육가정 · 구직자 · 어르신
홀수일: 저소득 가구 · 신혼·예비부부 · 장애인 · 소상공인
```

조 선택은 `date.toordinal() % 2` 로 계산합니다. 상태 파일이 없으므로 워크플로우가
하루 걸러 실패해도 다음 실행이 자기 차례를 스스로 압니다.

매일 8건 대신 격일 4건인 이유는 **건당 예산을 두 배로 쓰기 위해서**입니다.
Groq 무료 한도(약 일 10만 토큰)에서 하루 4~5건이면 건당 25,000토큰까지 쓸 수 있습니다.

### 인기 순서는 추정이 아니라 원천 값입니다

두 API 모두 조회수를 줍니다.

| 소스 | 필드 | 규모 |
|------|------|------|
| 보조금24 | `조회수` | 10,963건 |
| 중앙부처복지서비스 | `inqNum` | 461건 |

두 값은 스케일이 달라 직접 비교하면 안 됩니다 (보조금24가 큐를 통째로 차지합니다).
`queueing.popularity()` 가 **소스 안에서만** 순위를 매겨 0~1 백분위로 정규화합니다.
순위는 '서로 다른 조회수 값' 기준입니다 — 조회수는 상위 몇 건이 극단적으로 높은
꼬리 분포라, 건수 기준으로 나누면 중하위권이 전부 0 근처로 뭉갭니다.

점수 가중치(합 100): 조회수 45 · 지역 20 · 대상 15 · 마감임박 12 · 신설 8

> ⚠️ `view_count` 는 `schema._HASHED_FIELDS` 에 **넣으면 안 됩니다.**
> 조회수는 매일 바뀌므로 해시에 들어가면 매 실행마다 1만 건 전체가 '변경됨' 으로
> 잡혀 갱신 큐가 터집니다.

### 한 제도는 한 번만 발행됩니다

한 제도가 청년·구직자 양쪽에 걸치는 일이 흔한데, 발행은 한 번뿐이므로
'어느 테마의 오늘 1건으로 셀지' 를 정해야 합니다 → `primary_audience`.

- 원천이 직접 분류한 값이면(복지로 `lifeArray`·`trgterIndvdlArray`) **표기 순서 첫 번째**
- 키워드 추정이면 **본문에 실제로 몇 번 걸렸는지** 로 결정

딕셔너리 선언 순서를 그대로 쓰면 '청년' 이 항상 이겨 대표가 한쪽으로 쏠립니다.
대표가 아닌 테마 허브에도 `audiences` 로 계속 노출되므로 사라지지는 않습니다.

### 상태 3종

`시행중(active)` / `예정(upcoming)` / `종료(closed)` — `schema.resolve_status()`.

**매 실행마다 다시 계산합니다.** 저장된 값을 이어받지 않는 것이 핵심입니다.
매년 반복되는 사업은 작년 회차가 끝나 종료로 잡혔다가, 원천이 올해 기간으로
갱신되면 그날 자동으로 시행중/예정으로 돌아와야 합니다. 원장에서 물려받으면
한 번 종료된 제도가 영원히 종료로 남습니다. (`superseded` 만 예외 — 사람이 붙이는 값)

내용은 그대로인데 상태만 바뀐 제도는 `SyncResult.restatused` 로 분류되어
**저장해 둔 해설로 재렌더**됩니다 (`registry.load_prose`). LLM 호출이 없으므로
상한을 두지 않습니다 — 마감된 제도가 '시행중' 으로 남아 있는 것은 그 자체로
잘못된 정보라 밀리면 안 됩니다.

종료된 제도는 페이지를 남기되 `noindex: true` + `sitemap: false` 를 붙입니다.
마감된 금액·요건이 검색 결과에 남으면 지금 받을 수 있는 것으로 오인되기 때문입니다(YMYL).
이미 유입된 사람에게는 '끝난 제도' 라는 정보가 필요하므로 페이지 자체는 지우지 않습니다.

> ⚠️ **'예정' 은 신설 예정 정책이 아닙니다.** 두 원천 API 는 현재 운영 중인 서비스
> 목록만 줍니다. 여기서 잡히는 '예정' 은 "이미 등록된 사업인데 올해 접수가 아직
> 시작되지 않음" 입니다. 내년 신설 정책은 보도자료에서만 나오며, 별도 소스를
> 붙이기 전까지 이 사이트에 등장하지 않습니다.

### 메인 토픽

홈 최상단 히어로 1건. 종료되지 않은 제도 중 조회수가 가장 높은 한 건을
**매 빌드마다 Liquid 이 다시 뽑습니다** (`index.html`). 고정 목록을 두지 않는 이유는
사람이 고른 값이 곧 낡고, 그 제도가 종료되면 홈 최상단이 마감된 제도로 남기 때문입니다.
시행중과 예정이 같은 축에서 겨루므로 기대가 큰 예정 제도는 자연히 여기로 올라옵니다.

## 목 데이터 안전장치 ⚠️

지원금 정보는 YMYL 영역이라 **가짜 수치가 공개되면 실제 피해로 이어집니다.**

1. 목 레코드는 `is_mock=true` → 제도 페이지 상단에 **경고 배너** 렌더
2. 같은 플래그로 `<meta name="robots" content="noindex, nofollow">` 삽입
3. `search.json` 색인에서 제외
4. `daily-sync.yml` 첫 스텝이 `DATA_GO_KR_API_KEY` 부재 시 워크플로우를 **중단**

> ⚠️ 실 API 전환이 끝나 `.gitignore` 의 산출물 차단은 **해제되었습니다.**
> 이제 목 모드로 로컬 실행하면 가짜 제도가 커밋 대상이 됩니다.
> 커밋 전에 반드시 지우세요 — `_records/*.json` 의 `"is_mock": true` 로 구분합니다.
>
> ```bash
> rm -rf _programs _records _data/registry.json _data/queue.json \
>        _data/review_needed.json _data/incomplete.json
> ```

### 무엇이 커밋되고 무엇이 안 되는가

| 경로 | 커밋 | 이유 |
|------|:---:|------|
| `_programs/` | ✅ | 제도 페이지. 이게 있어야 배포됩니다 |
| `_records/` | ✅ | 레코드 + 해설 원본. 상태 변경 재렌더가 읽습니다 |
| `_data/registry.json` | ✅ | **발행 원장** — 중복 방지의 단일 진실 공급원 |
| `_data/taxonomy.json` | ✅ | 산출물이 아니라 `scripts/taxonomy.py` 파생값. 허브 생성기가 읽습니다 |
| `_data/queue.json` | ❌ | 매 실행 재생성 · 다시 읽지 않음. 1만 건이면 하루 수 MB |
| `_data/review_needed.json` | ❌ | 진단용. 실행 로그로 추적 |
| `_data/incomplete.json` | ❌ | 진단용. 실행 로그로 추적 |

> ⚠️ **원장(`registry.json`)을 다시 무시하면 안 됩니다.** 커밋되지 않으면 매 실행이
> "발행 이력 0건" 에서 시작해 같은 제도를 계속 새 글로 만듭니다. 중복 방지가
> 통째로 무너집니다.

## 검증한 것

### ① 중복이 구조적으로 불가능한가

```
1회차:  신규 25 · 변경 0 · 동일  0 · 필드누락 1 · 유사검토 1 · 범위밖 4
2회차:  신규  0 · 변경 0 · 동일 25 · 필드누락 1 · 유사검토 1 · 범위밖 4
        → "발행할 것도 갱신할 것도 없습니다. 오늘은 아무것도 쓰지 않습니다."
```

(목 데이터 31건 중 중앙부처 25건만 발행됩니다. 지자체 4건은 `REGION_SCOPE=national`
방침에 따라 보류, 1건은 필드 누락 격리, 1건은 유사 제도 검토 대기입니다.)

같은 소스를 다시 수집해도 신규 발행이 0입니다. 규칙이 아니라 **파일 경로가 제도 ID로 결정되기 때문**입니다.

3중 방어가 모두 발화하는 것도 확인했습니다.

| 계층 | 대상 | 결과 |
|------|------|------|
| 1 · ID 조회 | 재수집분 25건 | 전부 `unchanged` 로 흡수 |
| 2 · `content_hash` | 내용 동일 | 갱신 스킵, `last_checked` 만 갱신 |
| 3 · 유사도 | `청년 월세 한시 특별지원` vs `청년월세 한시 특별지원` | 유사도 1.0 → `_data/review_needed.json` 격리 (자동 병합 안 함) |
| 필수 필드 | 지원대상 누락 1건 | `_data/incomplete.json` 격리, 발행 안 함 |

### ② 환각이 차단되는가

원본에 없는 수치를 섞은 가짜 LLM 출력을 넣어 봤습니다.

```
입력:  "월 최대 20만 원을 12개월간 지원합니다. 신청자는 평균 340만 원의 혜택을 받습니다."
       "작년 기준 채택률은 87%였습니다"
       "심사는 3주 안에 끝나며 통과율은 62%입니다."
       "경쟁률은 4대 1 수준이며 8만 명이 신청했습니다."

판정:  위반 수치 4건(8, 62, 87, 340) · 문장 4개 폐기

출력:  "월 최대 20만 원을 12개월간 지원합니다."          ← 원본에 있는 수치라 생존
       (나머지 4문장 전부 삭제)
```

`3주` 의 `3` 은 원본 날짜(2026-**03**-02)에 있어 통과했지만, 같은 문장의 `62%` 가 걸려 문장째 폐기됐습니다.

### ③ 페이지가 제대로 나오는가

브라우저 렌더링까지 확인했습니다.

- 제도 상세: JSON-LD `GovernmentService`, 목 경고 배너, noindex, 정부 비공식 고지, 공식 창구 CTA, 한눈에보기 표, 자격 체크리스트, 신청 절차, 구비 서류, 신청 일정, FAQ, 관련 제도 내부링크, 최종 확인일 — 전부 렌더
- 마감된 제도(`2026 상반기 지역사랑상품권`)에 **접수 종료 배너** 자동 표시
- 가로 스크롤 없음 (`document.scrollWidth <= clientWidth`)

허브 필터링 결과:

| 허브 | 건수 | 검증 |
|------|------|------|
| `/support/` | 25 | 전체 |
| `/support/finance/` | 4 | 분야 필터 |
| `/who/youth/` | 12 | 대상 교차 필터 (홈 카드 숫자와 일치) |
| `/who/parent/` | 3 | |
| `/region/national/` | 25 | 중앙부처만 |
| `/deadline/` | 6 | 상시·마감분 정확히 제외 |

시도 허브 17개는 해당 제도가 없어 **생성하지 않았고**, 탐색바에서도 링크를 뺐습니다.
빌드 결과물의 내부 링크를 전수 검사해 **깨진 링크 0건**을 확인했습니다.

범위 확대·축소도 확인했습니다.

```
REGION_SCOPE=national,sido,sigungu  →  신규 4 · 동일 25   (보류분이 그대로 발행됨)
REGION_SCOPE=national (다시 좁힘)   →  신규 0 · 동일 29   (발행분은 계속 추적됨)
```

## 초기 설계안에서 바꾼 것

구현하면서 처음 설계와 달라진 부분입니다. 이유가 있는 변경이라 기록해 둡니다.
(REDESIGN.md 는 이미 아래 '실제' 쪽으로 갱신돼 있습니다.)

| 초기안 | 실제 | 이유 |
|--------|------|------|
| `scripts/queue.py` | `scripts/queueing.py` | `scripts/` 가 `sys.path` 에 들어가 표준 라이브러리 `queue` 를 가린다. `urllib3` 등이 이를 import 하므로 이름을 비켰다 |
| `_data/programs/{id}.json` | `_records/{id}.json` | Jekyll 은 `_data` 하위를 전부 파싱해 `site.data` 에 올린다. 레코드가 수천 건이 되면 빌드마다 낭비다. 밑줄 디렉터리는 Jekyll 이 통째로 무시한다 |
| 허브 33개 stub 파일 | `_plugins/hub_generator.rb` | 분류를 고칠 때마다 파일 33개를 손대야 한다. `_data/taxonomy.json` 하나를 진실로 두고 빌드 시점에 생성하며, 제도가 없는 시도 허브는 아예 만들지 않는다 |
| `/support/{category}/{slug}/` 수동 | `permalink: /support/:path/` | 파일 경로가 곧 URL. 별도 매핑이 필요 없다 |

`_plugins/` 를 쓸 수 있는 이유는 배포가 GitHub Pages 기본 빌더가 아니라 워크플로우 안의
`bundle exec jekyll build` 이기 때문입니다. 구 구조가 준 뜻밖의 이점입니다.

## 파일 지도

```
scripts/

### API 호출 수 — 220회 → 16회

첫 실 데이터 실행에서 파이프라인 스텝이 7분 12초 걸렸습니다. 원인은 보조금24를
**매 실행마다 전량 조회**한 것이었습니다. 두 가지를 고쳤습니다.

| | 이전 | 이후 |
|---|---:|---:|
| 목록 (`serviceList`) | 110회 | **11회** |
| 상세 (`serviceDetail`) | 110회 | **발행 대상 건수만** (하루 4~5회) |
| 합계 | **220회** | **16회** |

**① `perPage` 상향 + 페이지네이션 수정.** `PER_PAGE` 를 100 → 1000 으로 올렸습니다.
실제 호출로 `currentCount: 1000` 을 확인했으므로 10,963건이 11페이지에 들어옵니다.

더 올리지 않는 이유: 응답 하나가 1000건에 약 1MB 인데, 5000건이면 5MB 를 20초
(`TIMEOUT`) 안에 받아야 합니다. 호출 8회를 더 줄이자고 타임아웃 위험을 지지 않습니다.

상한이 바뀌더라도 안전합니다 — 1페이지 응답에서 서버가 실제로 준 건수를 보고
페이지 크기를 낮춥니다.

> ⚠️ 이때 종료 조건을 반드시 함께 고쳐야 합니다. 예전 조건은 "받은 건수가 요청
> 건수보다 적으면 끝" 이었는데, 서버가 perPage 를 깎는 순간(1000 요청 → 100 응답)
> **첫 페이지에서 멈춰 10,963건 중 100건만 수집하고도 성공한 것처럼 보입니다.**
> 그래서 응답의 `matchCount`(조건 적용 시) 또는 `totalCount` 를 채울 때까지 돕니다.
> 응답의 `perPage` 에코는 요청값을 그대로 되돌려 주는 서버가 있어 믿지 않고,
> 받은 행 수로 판단합니다.

**② 상세는 발행 직전에 건별로.** 목록에 지원대상·지원내용·선정기준·신청방법이 다
들어 있어 완결성 검사를 통과합니다. 상세가 더해 주는 건 구비서류와 온라인신청URL
뿐이라, 하루 4~5건에만 필요한 값을 1만 건어치 받을 이유가 없습니다.
`enrich()` 에서 `cond[서비스ID::EQ]` 로 1건씩 조회합니다 (복지로와 같은 패턴).

> ⚠️ `enrich()` 는 `content_hash` 를 다시 계산하지 않습니다. 해시는 목록 응답만으로
> 만들며, 여기서 채우는 값을 해시에 넣으면 다음 날 전부 '변경됨' 으로 잡힙니다.

odcloud 를 흉내내는 로컬 서버로 세 경우를 검증했습니다.

| 서버 동작 | 수집 | 총 호출 |
|---|---|---:|

어느 경우에도 조용한 데이터 손실이 없습니다. 실제 API 는 첫 줄에 해당하므로
**16회**로 동작하고, 나머지 두 줄은 향후 상한이 바뀌어도 깨지지 않는다는 보증입니다.

**API 하나로 충분합니다.** 보조금24가 중앙부처·지자체·공공기관·교육청 수혜서비스를 모두
담고 `소관기관유형` 으로 구분해 주기 때문에, 중앙부처 우선 단계에서는 `REGION_SCOPE` 가
범위를 걸러 줍니다. 복지로 기반 중앙부처복지서비스(`15090532`)는 겹치는 사업이 많아
유사도 검토 대기열만 키우므로, 필요할 때 `ENABLE_WELFARE_CENTRAL=1` 로 켜는 선택 어댑터로
돌렸습니다. (구현은 아래 §중앙부처복지서비스 참고 — 완료돼 있습니다)

설계상 주의한 점:

- `serviceDetail` 은 `cond[서비스ID::EQ]` 로 한 건씩 조회할 수 있지만, 제도 수천 건을
  한 건씩 호출하면 트래픽을 다 씁니다. **목록과 상세를 각각 통째로 페이지네이션해
  서비스ID 로 합칩니다.**
- `cond[수정일시::GTE]` 를 지원하므로 `SYNC_SINCE=YYYY-MM-DD` 로 **증분 동기화**가 됩니다.
  매일 전체를 다시 훑지 않아도 됩니다.
- 상세 조회가 실패해도 목록만으로 발행합니다(구비서류·신청URL만 빠짐).

#### 실제 데이터에서 드러난 것 (10,963건)

프로브로 확인한 목록 필드는 추정과 전부 일치했습니다. 다만 **실 데이터의 성격이
목 데이터와 크게 달라** 네 가지를 손봤습니다.

| 발견 | 처리 |
|------|------|
| `신청방법 = 기타 온라인신청\|\|방문신청` — `\|\|` 가 다중값 구분자 | `clean_text` 가 줄바꿈으로 분리 |
| `수정일시 = 20260129201825` — 14자리 타임스탬프 | `SYNC_SINCE` 를 `YYYYMMDD000000` 로 변환. 그대로 비교하면 증분 동기화가 어긋난다 |
| 지원내용·선정기준이 `○`/`-` 불릿을 가진 장문 (근로장려금 선정기준은 2천 자 초과) | 표에서 빼고 줄 구조를 살린 별도 섹션으로 렌더 |
| 구비서류·온라인신청URL 이 목록에 없음 | 이미 상세 병합으로 처리됨 |

**페이지 구조를 바꿨습니다.** '한눈에 보기' 표에는 짧은 메타(신청기간·소관기관·지역·
접수기관·문의처·근거법령)만 두고, 지원대상·지원내용·선정기준은 원문 줄 구조를 살려
각각 별도 섹션으로 렌더합니다. 2천 자를 표 한 칸에 넣으면 읽을 수 없습니다.

LLM 프롬프트에는 각 원문을 1,200자로 잘라 넣습니다. **검증(`verify.py`)은 잘리지 않은
전체 원문을 기준으로** 하므로 검증이 느슨해지지 않습니다.

#### 지원조건(JA* 코드)을 쓰지 않는 이유

`supportConditions` 응답은 `JA0101`, `JA0201` 같은 **코드 컬럼으로만** 오고 활용가이드에
코드표가 없습니다. `JA0110`/`JA0111` 이 정수형이라 연령 하한/상한으로 보이지만,
**추측해서 자격 요건에 쓰면 틀린 조건을 페이지에 싣게 됩니다.** 그래서 의미를 부여하지 않고
보류했습니다. 코드표를 확인하면 `CONDITION_CODE_LABELS` 를 채워 대상 분류 정확도를
높일 수 있습니다.

확인 방법: 지원조건을 받아 같은 서비스ID 의 `지원대상` 원문과 대조합니다.

```bash
python3 scripts/inspect_api.py --probe \
  "https://api.odcloud.kr/api/gov24/v3/supportConditions" --key "키" --rows 20
```

### 다른 API 의 ID_FIELD 를 확인하는 법

범위를 넓혀 새 API 를 붙일 때 씁니다. `scripts/inspect_api.py` 가 필드명을 뽑아
`ID_FIELD` 후보와 `FIELD_MAP` 초안까지 출력합니다.

```bash
# ① 활용가이드(Swagger/OpenAPI) 문서에서 — 키 발급 전에도 가능
python3 scripts/inspect_api.py --docs "https://infuser.odcloud.kr/api/stages/<번호>/api-docs"
python3 scripts/inspect_api.py --docs ./api-docs.json     # 내려받은 파일도 가능

# ② 실제 API 를 호출해 응답 1건의 키를 그대로 덤프 — 가장 확실
python3 scripts/inspect_api.py --probe "https://api.odcloud.kr/api/gov24/v3/serviceList"         --key "발급받은키" --rows 20
```

**②가 최종 근거입니다.** 문서와 실제 응답이 어긋나는 경우가 드물지 않아, 키를 받은 뒤에는
반드시 ②로 다시 확인하세요.

②는 여러 행을 받아 **행마다 값이 전부 다른 필드**를 찾아 줍니다. 고유 ID 의 정의가 그것이기
때문입니다. 다만 제도명·지원내용도 행마다 다르므로, 이름 패턴 점수가 높은 것(`★` 표시)을
우선 보세요. 표본이 클수록 판별이 정확해집니다.

눈으로 고를 때 판단 기준:

| 조건 | 설명 |
|------|------|
| 행마다 값이 다른가 | 같은 값이 반복되면 ID 가 아니다 |
| 값이 안 비는가 | 일부 행이 비면 파일 경로를 만들 수 없다 |
| 값이 안 변하는가 | **가장 중요.** 오늘과 내일 같은 제도가 같은 값을 갖는지. 조회 시각이나 정렬 순서에 따라 바뀌는 일련번호(`rowNum`, `순번`)는 ID 가 아니다 |
| 표기가 안정적인가 | 접두사·자릿수가 들쭉날쭉하면 `slug` 가 흔들린다 |

`rowNum` 류를 ID 로 잡는 것이 가장 흔한 사고입니다. 정렬이 바뀌면 어제의 3번이 오늘 7번이
되어 **모든 제도가 매일 새 페이지로 발행됩니다.** 하루 간격으로 두 번 호출해 같은 제도의
값이 그대로인지 확인하면 확실합니다.

### 중앙부처복지서비스 어댑터 (`15090532`, 선택)

**보조금24와 구조가 완전히 다릅니다.** 그대로 베끼면 동작하지 않습니다.

| | 보조금24 | 중앙부처복지서비스 |
|---|---|---|
| 응답 형식 | JSON | **XML** |
| 페이지 파라미터 | `page` / `perPage` | `pageNo` / `numOfRows` (최대 500) |
| 상세 조회 | 조건 없이 전체 페이지네이션 | **`servId` 로 한 건씩만** |
| 일일 트래픽 | 표기 없음 | **오퍼레이션당 100회** |
| ID_FIELD | `서비스ID` | `servId` (예: `WLF00001138`) |

#### 트래픽 100회가 설계를 결정했습니다

목록은 `numOfRows=500` × 100회 = 5만 건까지 받을 수 있지만, **상세는 `servId` 하나당
1회라 하루 100건이 한계**입니다. 제도가 1,284건이니 전량 상세 수집은 13일이 걸립니다.

그래서 상세를 수집 단계에서 받지 않습니다. `fetch()` 는 목록만 받고, 그날 실제로
발행·갱신할 레코드에만 `enrich()` 로 상세를 붙입니다. 발행 5건 + 갱신 10건 = 15회면
충분해 한도에 한참 못 미칩니다.

이 구조 때문에 두 가지를 따로 처리해야 했습니다.

**① 닭과 달걀 — `deferred_detail` 플래그**

목록 응답에는 `지원대상` 이 없습니다. 동기화 단계의 완결성 검사에 그대로 걸리면
`_data/incomplete.json` 으로 격리되어 **상세를 붙일 기회(`enrich`)조차 오지 않습니다.**
그래서 `deferred_detail=True` 인 레코드는 동기화 단계 검사를 유예하고,
발행 직전 `enrich()` 뒤에 다시 검사합니다. 그때도 비면 발행하지 않습니다.

**② 해시를 다시 계산하면 안 됩니다**

동기화는 목록 응답만으로 `content_hash` 를 만듭니다. `enrich()` 가 채운 상세를
해시에 반영하면 다음 날 목록 기준 해시와 어긋나 **모든 제도가 매일 '변경됨'으로
잡혀 무한 재발행**됩니다. `base.py:enrich()` 독스트링에 경고로 박아 뒀습니다.

**③ 상세가 목록 요약을 덮어씁니다**

목록의 `servDgst` 는 한 줄 요약이라 지원 금액이 없습니다. 빈 칸만 채우는 방식으로 두면
요약이 자리를 차지해 정작 중요한 '매월 최대 34만 원' 이 페이지에 못 들어갑니다.
상세가 값을 주면 덮어쓰고, 상세 조회가 실패하면 요약이 남아 최소한의 발행은 됩니다.

#### 목록 응답 필드 — 실제 호출로 확정 (전체 461건)

```

servNm              장애인자립자금대여
jurMnofNm           보건복지부               ← 소관부처

servDgst            (한 줄 요약)

srvPvsnNm           현금대여(융자)           ← 제공유형

**목록에는 지원대상·지원내용·선정기준·신청방법이 없습니다.** 요약(`servDgst`)뿐이라
`deferred_detail=True` 설계가 필수임이 실제 응답으로 확인됐습니다.

전체 461건입니다. 상세조회 100회/일 제한을 감안하면 전량 상세 수집에 5일이 걸리지만,
발행 상한(하루 5건)이 더 큰 병목이라 실제로는 문제가 되지 않습니다.

#### 원천 분류를 그대로 씁니다 — 키워드 추정보다 정확합니다

응답에 원천이 직접 분류한 값 3종이 옵니다. `taxonomy.map_bokjiro()` 가 이를 자체 분류로
직접 매핑하고, 표에 없는 값이 오면 기존 키워드 추정으로 넘어갑니다(안전한 실패).

| 원천 필드 | 예시 값 | 매핑 대상 |
|-----------|---------|-----------|
| `intrsThemaArray` | 생활지원, 일자리, 서민금융, 주거, 보육, 교육, 신체건강… | 분야(category) |
| `lifeArray` | 영유아, 아동, 청년, 노년 | 대상(audience) |
| `trgterIndvdlArray` | 장애인, 저소득, 다자녀, 한부모·조손 | 대상(audience) |

**`생활지원` 은 포괄 분류라 우선순위를 낮췄습니다.** 다른 주제가 함께 오면 그쪽을 씁니다.

```
생활지원,일자리,서민금융  → jobs      (생활·문화로 보내면 일자리 허브에서 사라짐)
생활지원,주거            → housing
생활지원 (단독)          → living
보육,보호·돌봄           → care
```

`청소년`·`중장년`·`다문화·탈북민`·`보훈대상자` 는 우리 대상 축에 대응 항목이 없어
**일부러 매핑하지 않았습니다.** 억지로 청년/어르신에 붙이면 대상별 허브가 부정확해집니다.

#### 상세 응답은 하이브리드 구조입니다 — 원문으로 확정

최상위에 본문 필드가 있고, **반복 섹션이 4종류** 따로 달립니다.

```
최상위 명명 필드
  servId servNm jurMnofNm
  tgtrDtlCn         ← 지원 대상
  slctCritCn        ← 선정 기준
  alwServCn         ← 지원 내용
  wlfareInfoOutlCn  ← 개요
  crtrYr(기준연도) rprsCtadr(대표문의) sprtCycNm srvPvsnNm …

반복 섹션 (각각 servSeCode / servSeDetailNm / servSeDetailLink)
  applmetList     × 5  신청 → 조사 → 결정 → 지급 → 사후관리 단계
  inqplCtadrList  × 2  문의처 (주소지 주민센터 / 보건복지상담센터 129)
  basfrmList      × 4  서식·안내 자료 (파일명 + 다운로드 URL)
  baslawList      × 2  근거 법령 (장애인복지법, 시행령)
```

태그명이 확정됐으므로 휴리스틱 대신 **명시적으로 매핑**합니다.
`applmetList` 의 섹션 이름은 `신청기관연락처목록` 처럼 꼬리표가 붙어 있어
`신청기관` 으로 정리한 뒤 내용과 이어 붙입니다.

파싱 결과:

```
신청 절차   신청기관 — 거주지 읍/면/동 주민센터…
            조사기관 — 담당 시·군·구, 금융기관에서 조사 및 심사
            결정기관 — 담당 시/군/구청 또는 금융기관에서 보장 결정
            사후관리 — 서비스 제공 이후 대상자의 상황 관리
문의처      주소지 읍·면·동 주민센터 / 보건복지상담센터 — 129
서식        개인정보 수집이용 동의서.hwpx / [별지 1의2] 소득·재산 신고서
근거 법령   장애인복지법 시행령 / 장애인복지법
```

**함정 하나:** `crtrYr` 은 기준연도(`2026`)입니다. 초기 후보 목록에서 구비서류
후보에 넣어 뒀었는데, 그대로 뒀으면 **'2026' 이 구비서류로 렌더**됐을 겁니다.
확정 과정에서 제거했습니다.

`basfrmList` 는 제출 서류만이 아니라 사업안내 문서도 섞여 있어, 섹션 제목을
'필요한 서류' 가 아니라 **'준비 서류·서식'** 으로 두었습니다. 다운로드 URL 은
만료될 수 있어 페이지에 노출하지 않고 공식 창구로 유도합니다.

근거 법령은 YMYL 신뢰도 요소라 '한눈에 보기' 표에 노출합니다.

> 이 구조를 `inspect_api.py` 가 처음엔 잘못 읽었습니다. 반복 요소만 뽑느라
> 최상위 본문 필드를 통째로 놓쳤고, `ID_FIELD = servSeCode` 라는 틀린 결론을
> 냈습니다. 지금은 **최상위 스칼라와 반복 섹션을 나눠서 출력**하고,
> `--raw` 로 응답 원문을 그대로 볼 수 있습니다.

### 지자체까지 넓힐 때

세 가지만 바꾸면 됩니다.

1. 추가 API 활용신청 후 `collect/adapters/__init__.py` 의 `REAL_ADAPTERS` 에 등록
2. `REGION_SCOPE` 를 `national,sido,sigungu` 로 변경 (워크플로우 입력 또는 env)
